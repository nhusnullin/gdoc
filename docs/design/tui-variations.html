gdoc v2.8.0 · design study · stderr only

gdoc, in the
terminal.

Six ways the binary could look to the person who typed it. Every window is drawn at 80 columns with gdoc's real words. Pick one by its number and borrow parts from the others, for example "3, but with the timeline progress".

stderr only

Everything drawn here goes to stderr. stdout still carries exactly one JSON object, untouched, so the skills read what they read today. The windows leave that object out.

80 columns, honestly

Each window is 80 columns wide and a faint line marks column 80. Today's help runs to 106 columns, so every direction wraps the long descriptions.

Plain when piped

Each direction shows its NO_COLOR and pipe version. With colour off, the six land on nearly the same page. That is on purpose.

Fonts people already have

Box drawing, block elements, braille and ✓ ✗ ● ○ ▸ ›. No Nerd Font glyphs, no emoji. Colours are truecolor with a 256 and a 16 colour fallback.

1

Quiet Pro Pick 1

Say less and line it up well. One blue accent does all the pointing.

Inspired by GitHub CLI, Vercel CLI, Stripe CLI.

Designer's view. The safe pick, and it will still look right in five years. The grouping by job does most of the work, not the colour. Green and red appear only on a step's outcome.

Engineering notes

Build cost 2/5: four SGR codes (bold, dim, one accent, reset) and a regrouped help list. No width or depth detection is needed.

  • To build: a group field on each row of the one command table in go/cmd/gdoc/commands.go, and helpList in go/cmd/gdoc/help.go:152-167 walking groups. The group stays out of the JSON from helpEntries (help.go:101-122), so no skill contract changes.
  • One accent from the 16 ANSI colours (for example cyan, the spinner colour at progress.go:30) works on every terminal, light or dark, because the user's theme picks the shade. Truecolor is optional, not needed.
  • Degrades well. Dim (SGR 2) is ignored by some terminals and the text just stays normal. At 80 columns it soft-wraps exactly as today, because nothing is boxed.
  • Piped and skill runs stay plain: cmdHelp writes to errOut (help.go:64-79), and tests pass a bytes.Buffer, which is never a terminal (progress.go:113-125). TestHelpIsOneObjectAndTheProseIsOnStderr (help_test.go:66) checks substrings only, so regrouping does not break it.
  • No rule collision. Fewest new words on screen of the six, which fits principle 4.

Needs: TTY check and NO_COLOR only (both exist today). No width, no colour depth, no new state.

2

Charm Pick 2

Pastel pills, rounded cards and room to breathe. Friendly, a little playful, still exact.

Inspired by Lip Gloss, Glow, Gum and Fang from Charm.

Designer's view. The warmest of the six. Pills and padding cost rows: help grows to about 60 lines. It suits colleagues who are not engineers and run gdoc through a skill once a week.

Engineering notes

Build cost 3/5: a box renderer with hard word wrap, three palettes per colour (truecolor, 256, 16), and golden tests for each.

  • To build: Lip Gloss is out (allowlist at go/boundary/boundary_test.go:369-388), so boxes, padding and pills are hand-rolled: a display-width function that skips escape codes, a word wrapper, and a border drawer. Roughly 200 lines on top of the foundation.
  • Width is required. Command summaries run 60 to 90 characters, so inside a padded box at 80 columns most wrap to two lines. A box that soft-wraps instead breaks its right border, so the wrap must be ours.
  • Light backgrounds fail. Pastels near 0.6 luminance (a typical pink or lavender) give about 1.6:1 contrast on white, which is unreadable, and the binary cannot learn the background (see foundation). Pills with a pastel background and dark text survive both; pastel text does not.
  • On a 16-colour terminal pastels collapse to the theme's bright magenta and cyan, which reads loud, the opposite of the intent. Pills become blocks of the theme's colour.
  • Windows: legacy console fonts may lack the rounded arcs (U+256D to U+2570) and show boxes or question marks. Windows is built by make dist (Makefile:50) but not yet released (release/platforms:8-14).

Needs: width detection, colour depth detection. No new state.

3

Altery House Pick 3

gdoc looks like the documents it makes: navy, teal, orange and peach, straight from the house style.

Inspired by go/internal/house/house.yaml: the navy headings, the teal third level, the orange running head, the grey header rule and the peach and blue-grey table fills.

Designer's view. The branded pick. The navy banner is loud, so it appears only on help. Other commands get a one-line band. Help groups are numbered like the house headings, and the flag table copies the house table header.

Engineering notes

Build cost 3/5: brand hex needs depth detection and a 256 and 16 fallback, and the navy fails on dark terminals, so it needs a second, terminal-only palette.

  • The colours exist: go/internal/house/house.yaml:19-27 (navy #22265F, teal #549F99, orange #FF771C). Teal and orange read on both backgrounds (about 6.8:1 and 7.9:1 on black, 3.1:1 and 2.7:1 on white, so bold only on white). Navy is about 1.4:1 on black: invisible on a dark terminal. So "brand colours from house.yaml" holds for two of three, and navy needs a lighter terminal tint that house.yaml does not carry.
  • Reading the colours from internal/house at run time ties help to the docx style file. A house-style test must state its value as a literal (CLAUDE.md invariant, TestHeadingNumberingIsTheLiteralFormat), so the terminal palette tests repeat the hex values rather than read the constants.
  • The notice line is easy to style: it is one string written in one place (help.go:70-72). A filled callout block needs width to pad the background to an even edge. A left bar (one coloured glyph per line) needs no width and drops the cost to 2.
  • The wordmark banner adds lines to every help and to bare gdoc (main.go:104). Principle 4: "if the reader does not need it, remove it". One coloured line that keeps the version (the reason versionHeading exists, help.go:142-150) passes; a multi-line banner is hard to defend.
  • On 16 colours the brand is gone: teal becomes the theme's cyan and orange the theme's yellow or red.

Needs: colour depth detection; width only for a filled callout. No new state.

4

Panels Pick 4

Everything in a titled box, help as a two-column table, and a status bar on the last line.

Inspired by k9s, btop, lazygit. Tokyo Night colours.

Designer's view. The most dashboard-like. A table keeps long descriptions tidy at 80 columns. It stays static, because gdoc never reads stdin. The account in the status bar needs help to read the token file, which it does not do today.

Engineering notes

Build cost 5/5: a small layout engine, a pinned status bar, and an account name the binary cannot know without a network call or a new OAuth scope.

  • Hard blocker for the status bar's account. The token file carries no account: Account is a pass-through field gdoc never writes (go/internal/auth/auth.go:59-76), and the token on this machine has no such key. gdoc asks only for the Drive and Docs scopes (go/internal/auth/login.go:43-44), so there is no id_token or email. Getting it means drive.about.get, which the guard refuses (go/internal/guard/doc.go:460-461), or a new openid email scope and a fresh consent for every user. Either one is a DECISIONS.md entry. A network call during help also breaks "help is the one command that asks unasked, once in 24 hours" (CLAUDE.md invariants).
  • Version and channel are free: releaseVersion (main.go:40-45) and Version.IsStable (go/internal/update/version.go:105), since the channel is the patch number. Token present or expired is free too, from auth.Status, a local file read.
  • A bar pinned to the bottom row needs the row count (ioctl again) and a scroll region or the alternate screen. The alternate screen erases help on exit, which defeats help. A scroll region leaves the terminal broken if gdoc is killed mid-run.
  • Two-column help does not fit 80 columns: about 38 columns per side against 60 to 90 character summaries means three lines each, or truncation that drops words a skill author relies on. It must fall back to one column below roughly 120 columns.
  • Box drawing on every line breaks the moment one line is too long, so every string (paths, error reasons from progress.go:329) must go through our own wrap and width code.

Needs: width and height detection, colour depth detection, and state the binary does not have (the account name).

Phosphor Pick 5

An amber CRT. A block-letter banner, boot-log progress and uppercase labels.

Inspired by the VT220, the systemd boot log, BBS banners. The scanlines and glow exist only in this preview; a real terminal draws flat colour.

Designer's view. The fun one. Memorable in a demo and tiring every day. Best as an opt-in theme, not the default. Failure uses reverse video instead of red, so it stays one colour.

Engineering notes

Build cost 2/5: two colours and a fixed ASCII banner are cheap; the cost is in what it breaks, not in the code.

  • To build: an embedded block-letter banner (pure ASCII, so it survives every Windows font), uppercase labels in helpList and helpOne (help.go:152-195), and amber or green from the foundation's SGR helpers.
  • Light backgrounds fail. Amber and bright yellow on white are near 1:1. The binary cannot detect the background. The workaround, painting a black background (SGR 40), needs width to pad every line to the edge and overrides the user's theme.
  • Amber is not one of the 16 ANSI colours. On a 16-colour terminal it becomes the theme's yellow, which varies from mustard to lemon. True amber needs 256 or truecolor.
  • Principle 4 collision: a five or six line banner on every gdoc help and on every bare gdoc (main.go:104) carries no information. Uppercase labels also read slower than mixed case.
  • The banner must stay off non-terminal stderr. Help is the first call of every skill session (notice.go:3-6), and those runs must stay plain (cmd/gdoc/doc.go:349-351).

Needs: colour depth detection for true amber; width only if it paints its own background. No new state.

6

Timeline Pick 6

Progress reads top to bottom like a deploy log, with durations on the right. Help reads like a tree.

Inspired by Vercel and Railway deploy logs, tree, the Tailwind slate scale.

Designer's view. The strongest update of the six: a vertical line and a time per step make a slow download feel calm. The tree shows the four groups at a glance. Calm colours that survive a light profile.

Engineering notes

Build cost 3/5: progress.go already has the step model; the work is connector rows in the redraw, a clock per step, right-aligned durations, and a tree printer for help.

  • Builds on what exists. progress.go already has pending, running, done and failed states and an in-place redraw (progress.go:57-71, 288-313). The timeline is a different stepLines, plus connector rows that the redraw counts in p.drawn, or the cursor moves up too few rows.
  • Durations need a start time per step (new, small) behind an injectable clock, or the tests are not deterministic. Keep durations on the terminal path only: TestAnUpdateNarratesItsStepsOnStderr (update_test.go:637) pins the plain lines byte for byte.
  • Right alignment needs real width. Today the live width is a hardcoded 78 (progress.go:47-50). Without width, durations sit at a fixed column, which is still fine at 80 columns.
  • Today only gdoc update draws progress (update.go:235-245). The value grows only if propose, publish or restyle adopt the step list too, which is separate work.
  • Help as a tree (├ ╰ glyphs, all width 1) is cheap with groups from quiet-pro; flags as leaves make the full help two to three times longer, so keep flags for gdoc help <command>.

Needs: width detection (for right alignment), a clock per step. No colour depth detection beyond the 16 colours used today.

⚙

What every direction sits on

The senior engineer's view: the shared base, its size, and the six ranked by value for cost.

Hard facts every direction sits under

  • Three modules only: etree, go-yaml, goldmark (go/go.mod:5-10), each named in allowedModules (go/boundary/boundary_test.go:369-388). TestNoThirdPartyDependencies (:392) fails on a fourth, including a go.sum entry. TestAllowedModulesAreReallyRequired (:412) fails the other way. SPEC.md says "Everything else is the standard library" (docs/v2/SPEC.md:62-63). So Lip Gloss, Bubble Tea, termenv, x/term, fatih/color and golang.org/x/sys are all out without a DECISIONS.md entry and a SPEC reason. x/sys is not in go.mod or go.sum.
  • stdout is one JSON object (main.go:64-78). All human words go to stderr: help (help.go:71-73), the login link (auth/login.go:245, pinned by TestLoginPrintsTheURLToStderrNotStdout, login_test.go:27), and the update steps (TestAnUpdateNarratesItsStepsOnStderr, update_test.go:637). No direction needs to change that.
  • Non-terminal stderr stays plain, NO_COLOR honoured: cmd/gdoc/doc.go:349-358 and progress.go:113-131, pinned by TestAPipedRunPrintsOneLinePerFinishedStep and TestNoColorKeepsTheRedrawAndDropsTheColour.
  • No external programs: TestNothingRunsAnExternalProgram (boundary_test.go:308-321) bans os/exec and syscall/js. So no tput or stty. Plain syscall and unsafe are not banned, and cmd/gdoc/read.go:20 already imports syscall.

Width without x/term

  • darwin and linux: syscall.Syscall(syscall.SYS_IOCTL, fd, syscall.TIOCGWINSZ, uintptr(unsafe.Pointer(&ws))). Both constants are in the stdlib for darwin and linux. On darwin this goes through libc's syscall(), which Apple marks deprecated but still ships. About 20 lines in a //go:build darwin || linux file. Linux matters because CI runs on ubuntu (.github/workflows/go.yml:12).
  • Windows: syscall.NewLazyDLL("kernel32.dll") and GetConsoleScreenBufferInfo, about 30 lines in a _windows.go file. CI cross-builds it on every push (go.yml:27-28, Makefile:50), so a compile error is caught.
  • COLUMNS is a weak fallback: bash and zsh set it but do not export it, so a child process usually sees it empty. Use it as an override (handy in tests), then ioctl, then 80.
  • Existing gap, worth a backlog item: on Windows, isTerminal is true for a console, and progress.go already writes ANSI codes there without setting ENABLE_VIRTUAL_TERMINAL_PROCESSING. Windows Terminal copes; the classic console prints raw escapes. The foundation should set that mode once, through the same lazy kernel32 load, and fall back to plain if it fails. This belongs on docs/backlog/windows-rollout-checklist.md.

Colour depth and background

  • Depth: COLORTERM is truecolor or 24bit gives 24-bit; TERM ending -256color gives 256; else 16. TERM=dumb gives none. All env reads, no I/O.
  • Background: the OSC 11 query needs a reply read from the terminal, and the binary never reads stdin (CLAUDE.md invariants). COLORFGBG is set by a few terminals only, not by Apple Terminal. So treat the background as unknown. Palettes must use mid-luminance colours that read on both (teal and orange qualify, navy and pastels do not), or stay with the 16 ANSI colours, which the user's theme already tuned for their background.

The shared foundation

One new package, go/internal/tty, stdlib only. Inside: a Profile (is a terminal, colour on or off, depth, width) from one Detect(w io.Writer); isTerminal and wantsColour moved out of progress.go; SGR helpers (bold, dim, fg, bg, reset) that return the bare string when colour is off; hex to 256 and hex to 16 fallback; a visible-width function that skips escape codes; a word wrap; the two width files and a fallback file for other platforms. About 250 to 300 lines of code and a similar amount of tests.

  • It needs doc.go with exactly one Package tty comment that names a test per rule (CLAUDE.md, TestEveryPackageHasExactlyOnePackageComment). The build-tagged files open with a file comment separated by a blank line from package.
  • New rows in CLAUDE.md's two tables, kept under 300 lines (TestCLAUDEmdIsUnderTheCeiling, TestTheTaskMapNamesFilesThatExist).
  • Tests: a pipe and a buffer are plain; NO_COLOR and TERM=dumb turn colour off; depth from COLORTERM and TERM, as literals; hex to 256 and 16 against literal codes; width from COLUMNS, then 80; wrap never exceeds the width; visible width ignores escapes.
  • Two boundary siblings in go/boundary: no \x1b[ literal outside internal/tty (like TestNetHTTPStaysInItsRooms), and every command's human text written into a buffer carries no 0x1b byte. The existing progress tests (TestOnlyACharDeviceIsATerminal, TestATerminalRunRedrawsInPlaceAndColours) move or gain siblings in the new package.
  • Any milestone plan for this carries the Principles block. Principle 4 is the one most of these directions strain.

Ranking by value for cost

  1. quiet-pro (2): grouped help is the biggest readability gain, and it is safe on every terminal and background.
  2. timeline (3): grows the progress code that exists. Worth it once a second command draws steps.
  3. altery-house (3): brand recognition, but navy fails on dark terminals and the banner fights principle 4. A teal accent on top of quiet-pro gets most of the value for less.
  4. phosphor (2): cheap code, little value, fails on light backgrounds, banner fights principle 4.
  5. charm (3): looks best in a screenshot, fails on light backgrounds and on 16 colours, and needs the full wrap and box engine.
  6. panels (5): highest cost, worst at 80 columns, and the account in the status bar is a hard blocker without a new scope or a guard change.

A reasonable pick: quiet-pro for help, the timeline marks for progress, and teal from house.yaml as the one accent.
