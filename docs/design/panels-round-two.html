Question A: how much safety does --json buy?

Short answer: yes, it is the safety net, and you need it on help only. No check can tell a person at a terminal from an agent behind a pseudo-terminal. A pseudo-terminal is a terminal by definition, so isatty says yes for both. Only the caller can say which it is.

How loudly it breaks without the flag

Quietly. That is the reason to keep the flag. Every SKILL.md says the same thing about the first call: no version means a build from source, so say it once and carry on (for example skills/gdoc-review/SKILL.md:41-43). A PTY agent that gets no object will most likely read "no version" and carry on. The needs gate is then skipped without a word. The flag table is still readable as prose, so most later calls would still work. The one real loss is the version gate, and it is lost in silence. That is uncertainty resolving to "act anyway".

A script behind a PTY fails loudly: jq on empty input errors. That case is rare and the error is visible.

What --json costs

  • One flag in help's table entry. It then shows in help's own usage line and in the completion scripts. TestHelpTakesWordsAndNoFlags (help_test.go:249) changes, and its rule "nothing is accepted and ignored" still holds.
  • An older binary refuses help --json, so the skills change in the sitting that cuts the tag, and their needs line names that release. This is the order the 2026-10-02 entry used for --folder (docs/v2/DECISIONS.md:3004-3009). The failure is loud: exit 1 and an error naming the flag. The refusal object still carries version, because run() sets it on every object (main.go:72). So a skill that reads the version from a refusal too still stops with the right sentence.
  • No test ties a flag a skill uses to the release that added it. TestNoSkillNeedsAReleaseNobodyCut only caps needs. Forgetting the bump would give a confusing refusal on a colleague's older binary. It is a one-line manual step, worth naming in the plan.
  • Tokens: seven characters on two or three calls per session. Nothing.
  • One new test beside the call-line test, which must read the inline prose mentions too, such as "Run $GDOC help export".

The options, from least to most safety

  1. No flag, isatty only. Safe for Claude Code, scripts and most CI. Quiet failure for PTY agents and the desktop terminal tool. Not safe enough, because the failure skips the version gate without a word.
  2. --json on help only, skills pass it. Closes the gap for every skill caller, whatever its harness. Costs one flag and one release-ordering step. This is the minimum that is safe.
  3. --json on every command as a no-op except help. Reject. It is a flag accepted and ignored on fifteen commands, which the strict parser exists to prevent. It adds a line to every help entry and every completion. It buys nothing, because no other command drops its object.
  4. An env var such as GDOC_JSON=1. It has one real strength: an older binary ignores it and prints the object anyway, so there is no release-ordering cost. Its weaknesses: a misspelt name is ignored in silence, which is the opposite of how gdoc treats input; it is ambient state a person can leave set and forget; and Claude Code does not keep env vars between Bash calls, so a skill still writes it on every line. Not now. Add it later if a third-party agent needs to opt in without editing skills.
  5. Other heuristics.
    • "Also print the object when stdin is not a terminal." Adds nothing. Under every PTY agent stdin is the same tty. Under Claude Code stdout is already a pipe. It also has gdoc look at stdin, a stream it promises never to touch, and M14 is narrowing that rule already. Reject.
    • "Print the object when TERM=dumb." Harmless, and right for Emacs shells and some harnesses. It is partial: tmux and IDE terminals set a real TERM. Optional, never a substitute for the flag.
    • Detecting an agent by env (CLAUDECODE, CI). The draft already rejects it, and it is right to: it is a rule about identity.

Recommendation

Option 2, with three small additions that make it safe rather than nearly safe.

  1. Drop the object only when help answered. On a terminal without --json, stdout is empty only for ok: true. A refusal (gdoc help sing) and the panic envelope still print their object. There is no Panels view for a refusal, so dropping its object would print nothing and exit 1. This also keeps the invariant easy to state: an empty stdout always means exit 0.
  2. --json also means plain stderr. With the flag, stderr gets today's plain prose, even on a terminal. A PTY agent then gets exactly today's bytes, object and prose, with no escape codes in its stream. The draft styles stderr by the stderr check alone (decision-draft-help-on-a-terminal.md:45-47), which would put Panels escapes into a PTY agent's capture.
  3. Fix the skill wording. "No object at all" is a failed call, not a build from source. Read version from the object whether it says ok or not.

Question B: bare gdoc on a terminal

Recommendation: keep the object. Change nothing for bare gdoc.

  • It is a failure, and every failure should stay an object. A failing run with empty stdout is close to the crash shape that doc.go:384-385 calls "the one shape no caller can read". Only the exit code would differ. The rule "drop only on ok: true" from Question A keeps it out.
  • "Exit 0 iff the object says ok" has nothing to check when there is no object. With the rule above, the only empty stdout is a successful help, so the invariant reads cleanly: empty stdout means help answered on a terminal, and the exit is 0.
  • A script that calls bare gdoc by mistake has stdout on a pipe. It gets the object either way, so this choice does not affect scripts.
  • The pins stay as they are. TestNoArgumentsFails and TestBareGdocStillFailsAndPrintsTheHelpToStderr (help_test.go:226) run on buffers, which are never terminals, so they pass under any terminal rule. Keeping the object means their doc comments need no exception either.
  • The cost is one JSON line under the help, for a person who typed a command that does nothing. It is about 200 characters. That is acceptable for a mistake. Making bare gdoc the same as gdoc help with exit 0 would reverse the M7d reasoning. That is a separate decision, and I would not take it.

On consistency: gdoc and gdoc help now end differently on a terminal. That is correct. One is a question that was answered, the other is a mistake.

M14

M14 narrows "one object reaches stdout" to "every CLI command", with gdoc mcp writing JSON-RPC instead, and routes mcp in main() before run(). This idea adds a second exception inside run(). Write the CLAUDE.md line once, naming both exceptions, after M14 lands.

Corrections to the draft

  1. The object is about 7.4 KB, not 700 characters. decision-draft-help-on-a-terminal.md:19. A checkout build's gdoc help writes 7,369 bytes to stdout. gdoc help publish writes 534. The real number makes the case stronger.
  2. Help cannot see stdout. Lines 31-34 say help "decides by what stdout is". cmdHelp gets only errOut (help.go:64). run() owns stdout and prints every result through emit.Print (main.go:67-78). The drop has to happen in run(), the same choke point the panic envelope depends on. The decision should name that place.
  3. Refusals are not covered. Lines 31-34 and 48-50 say what a terminal gets when help answers. They do not say what gdoc help sing gets. As written, a refusal on a terminal would print no Panels, no object, and exit 1. Add: only ok: true drops the object.
  4. The --help alias skips the parser. Lines 39-42 add --json to help. But --help and -h are answered before the parser runs (main.go:111-113), and helpWords drops everything except the command it found (help.go:257-262). So gdoc read --help --json would ignore --json in silence and fall back to the terminal check. gdoc --help --json would be refused as unknown command "--json". The alias path must read --json too, with a test.
  5. Styling should not follow the stderr check alone. Lines 45-47. With --json, stderr should stay plain. Otherwise a PTY agent that passes the flag still gets escape codes in its stream.
  6. Two definitions of "terminal". Lines 35-38 choose isatty for help. progress.go:113-125 keeps the character-device bit, pinned by TestOnlyACharDeviceIsATerminal and stated at doc.go:351-353. One package should not hold two answers. Move progress.go to the same check in the same change: today gdoc update 2>/dev/null draws a live list into /dev/null.
  7. Platforms. Lines 36-37 name darwin and linux. make dist ships darwin arm64, darwin amd64 and windows amd64 (Makefile:48-50). Linux matters only because CI builds and tests there. Say that, so nobody thinks linux ships.
  8. The exit-code invariant needs the exception too. Lines 55-59 amend "one object reaches stdout". They do not amend "the exit code is 0 iff that object says ok" in CLAUDE.md and doc.go:13-14. With no object, that sentence has nothing to check. Suggested wording: "An empty stdout means help answered on a terminal, and exits 0."
  9. Warnings would vanish. The notice's warnings ride in the object (help.go:69-77), for example an unreachable GitHub. On a terminal without the object, nobody sees them. The Panels view should print them.
  10. Release order is loud, not silent. Lines 94-97 say a skill passing --json to an older gdoc "fails". True, and the refusal still carries version, so the needs gate still works if the skill reads it from a refusal. Worth saying, because it makes open question 3 smaller than it looks.
  11. Tests. The list at lines 78-86 misses three: a refusal on a terminal still prints its object; <command> --help --json prints the object; --json keeps stderr plain on a terminal. CI has no tty, so the terminal tests need an injected terminal check. The real isatty is then pinned only by TestDevNullIsNotATerminal and the pipe cases. Say so in the decision.

Width Team recommends: this rule

One rule, which picks one of three layouts by the terminal's width. The windows show gdoc help in each band.

gdoc reads the width once, from stderr, through TIOCGWINSZ on macOS and Linux and the console call on Windows. COLUMNS overrides it. If neither answers, it assumes 80. The output is static, so a resize after the run does not reflow it, the same as any CLI.

The rule the team recommends. Draw at min(width, 100). Use two columns at 80 and wider. Stack from 50 to 79. Below 50, print the plain text, because two borders and two pads cost 4 columns and the words wrap into slivers.

  • Why cap at 100. A wider box adds only empty border. Lines past 100 characters are slow to read.
  • Why two columns at 80. The description column is 55 wide, so most commands take two rows. Stacked at 80 takes two or three rows per command too, plus a row for the name. Two columns is the shorter of the two.
  • Why the left column is 18 wide. The group titles sit in the left part of each rule, and "Write into a doc" needs 16 plus its padding. Command names need only 11.

Status bar Nail's pick: no bar

Decided: no status bar, and nothing about sign-in on help.

Why. Everything the bar carried is already said somewhere better.

  • The version is in the top border of every help box.
  • The channel is in the version: a stable release ends in .0.
  • Signed in, signed out and scopes missing belong to auth status. After M14 the account goes there too.
  • Help stays free of the token file, so it reads only the release stamp, as today.
  • On update the step marks and the result line already say how a run ended. On auth login a final ✓ signed in line does it.

Colour Team recommends 4A

One palette, because gdoc cannot know the background.

Asking the terminal for its background (OSC 11) means reading its reply from stdin, and gdoc never reads stdin. COLORFGBG is set by few terminals. So the palette must read on both. Depth comes from the environment: COLORTERM=truecolor or 24bit gives truecolor, a TERM ending in -256color gives 256, anything else gives 16.

4A: one palette for both backgrounds. Round one used Tokyo Night's own colours. Its text colour #C0CAF5 is about 1.5:1 on white, so it vanished on a light terminal. Round two keeps the hues and changes two things.

  • Text is never coloured. Command names, descriptions and JSON use the terminal's own foreground (SGR 39), which the person already tuned for their background.
  • Accents sit at middle brightness. Each one is at least 3.4:1 on white and 3.9:1 on Tokyo Night. That is enough for bold titles, glyphs and short labels, which is all they colour.

Bare gdoc Nail's pick 5b

Today bare gdoc prints the help to stderr, an ok:false object to stdout, and exits 1.

Bare gdoc does not run the release check, so it never shows the notice. Both options keep the plain text and the object exactly as today on a pipe.

Nail's pick: 5b. The rule: on a terminal without --json, a help screen replaces the object. Help screens are help when it answers and bare gdoc. Every other result still prints its object, refusals included. Bare gdoc shows no hint line, because gdoc --json is not a valid call. Exit 1 tells a script it failed. The screen shows only the help.

Help's stdout on a terminal Nail's pick 6b

What appears under gdoc help publish when you type it.

In all three, a pipe still gets the object, and --json prints it anywhere.

Nail's pick: 6b, drawn on stderr. The hint is the last line of the help: Add --json to print the JSON object a skill reads. It is dim when colour is on. It shows whenever help dropped the object, including NO_COLOR or TERM=dumb on a terminal, where it is plain.
