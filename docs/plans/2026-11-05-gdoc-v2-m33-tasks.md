### The design

- **One parser, `go/internal/tasks`, new.** `Parse(source string) (Task,
  error)` takes an item's markdown source text, not goldmark's inlines,
  because GFM's linkify turns `@anna@x.com` into an autolink. It answers the
  words, the owner as written, the due date, and each token's byte span in
  the source, or a refusal naming what is wrong. `Owner.Resolve(domain)`
  answers the address, or a refusal naming the `domain` setting. No network,
  no settings import. body and propose both call it.
- **The docx keeps the tokens.** The decision says publish keeps the docx as
  it is, so `gdoc build` and a publish whose last batch fails both leave the
  owner and the date in the text, and nothing is lost. body only strikes a
  done item's words and lists the tasks: `Result.Tasks` holds each task's
  words, owner as written, date, done, and the token text as rendered. A task
  body refuses by name: a nested task, a task in a numbered list, a list that
  is a task list inside another list, and a token inside emphasis.
- **Publish resolves before it sends.** `cmdPublish` resolves every owner
  against `a.set.Domain` after `renderNote` and before the upload, so a bare
  owner with no setting sends nothing. `build` resolves nothing.
- **Publish converts after the upload, from `verify`'s read.** No second read
  before the batch. Take the paragraphs that open with `☐ ` or `☒ ` in
  order; if their count or words differ from `Result.Tasks`, send nothing and
  report `Checks.Tasks` false. Otherwise one batch:
  1. For each run of adjacent task paragraphs, `deleteParagraphBullets` over
     the run, then `createParagraphBullets` with `BULLET_CHECKBOX` over it.
     Measured: a checklist request over part of a list turns the whole list,
     and taking the bullets off first keeps the plain items as they were.
     Bullets move no index, so these go first, at the read's indexes.
  2. Then per task paragraph from the last to the first, and inside one
     paragraph from the end back: each token's text is deleted and its chip
     inserted at the token's start, then the two ballot characters at the
     paragraph's start are deleted.
  A date is sent as noon UTC on that day with
  `DATE_FORMAT_MONTH_DAY_YEAR_ABBREVIATED`, as the probe did. Then one read,
  the checklist items and chips counted against `Result.Tasks`, and that read
  handed to `mark`. `Checks.Tasks` is true for a note with no task, and
  `Verified` is computed after this step. No new presence step name:
  `TestAPublishStepsAreTheFixedNamesInOrder` holds the four.
- **The reader knows a checklist.** `rawList` decodes `glyphSymbol` and
  `glyphFormat`; `Bullet.Checklist` is a level with `GLYPH_TYPE_UNSPECIFIED`,
  no symbol and format `%0`. `rawDateElement` decodes `timestamp` and
  `timeZoneId`. view prints a checklist item `- [ ] `, and a person chip with
  an email or a date chip that ends a checklist item, with only spaces before
  it back to the words or the other chip, as `@email` and `YYYY-MM-DD`: the
  day in the chip's own `timeZoneId`, or UTC when it has none. A person chip
  with no email, and any chip elsewhere, prints as today. One warning per read
  that holds a checklist: "a checklist's ticks are not in Google's answer, so
  every item prints unticked". Export inherits it.
- **propose takes a task list.** A block may hold one task list, one level
  deep, unticked only: `[x]` is refused, because a block has no strike. The
  chips go last in the batch, from the last to the first, after any
  `deleteContentRange`, so the replace shift stays as it is. Measured: text,
  checklist and chip in one SUGGEST batch come back as one suggestion id. The
  block read-back learns chips: each paragraph's text is compared with its
  chips taken out, and every chip in the block must carry the block's
  suggestion id, or the run stops (the trust guardian's condition). In chat a
  bare owner is refused, because the card shows what is written and a
  resolved domain would not be on it.
