# Hand gdoc whole jobs, not single commands

The best route is to stop letting the model drive gdoc one command at a time. Give it whole jobs instead. gdoc hands the model one work packet: the marked threads, the paragraph each is anchored to, the pending suggestions that overlap it, and the paired note. The model sends back one response plan, and gdoc posts it, checks it and reports in a single call. Wake the model only when there is real work. Run routine work in a small, fresh context. Serve that one set of operations through thin adapters: the CLI for Claude Code and the terminal, `gdoc mcp` for Claude Desktop (and later for Claude Code), and the presence record for the menu bar app. The measurements explain why. gdoc takes about a quarter of a live window, a process starts in 20 to 60 ms, and the rest is the model taking turns, each one re-reading 257k to 725k tokens of context. With job-sized commands, the estimate is a reply in 20 to 35 s instead of about 55 s (est.), and a live hour at about 35% fewer tokens (est.). Switching the transport (CLI, MCP or a daemon) moves these numbers very little. In 2026 re-tests, MCP and CLI came out within a few percent. The largest speed gap is one nobody measured: a comment written while no session is open waits until somebody starts one. Closing that gap needs a watcher that lives outside a session. That breaks the rule "there is no watcher", and only Nail can decide it. This is also where the senior engineer and Codex disagree most. My advice is to measure that gap before building for it.

## Model turns, not gdoc, set the clock

The clearest measurement is the live window. It runs from the moment a `comments --wait` call returns to the last write. Over 13 windows the **median was 52 s and the p90 about 88 s**. gdoc's own calls took **174 of the 700 s in total, which is 25%** ([baseline](how-ai-skills-talk-to-gdoc-notes/baseline_today.md)). Codex checked this arithmetic and agrees. Codex also gave one correction that matters: the other 75% is elapsed time minus gdoc time. It holds model inference, but also other tools and scheduling. So it is not all inference ([Codex](how-ai-skills-talk-to-gdoc-notes/codex_second_opinion.md)). gdoc's own speed is fine. Median times are **read 1.3 s, reply 1.3 s, suggestions 1.0 s, comments 2.0 s, propose 6.8 s (p90 17.4 s) and publish 10.3 s**, and the binary starts in about 20 to 60 ms. The `propose` and `publish` medians include runs that were refused at 0 ms, 7 of 34 and 3 of 8 runs. So a successful write is a little slower than these medians show ([baseline](how-ai-skills-talk-to-gdoc-notes/baseline_today.md)).

The cost is in how many turns a job takes. The skills open with `gdoc help --json` (9.6 KB), often add `help <command>` before each command, and then run 3 to 12 single-shot commands. A one-shot review with two `ai?` comments, one `ai!` comment and one proposal makes **about 11 gdoc calls and 15 to 20 model turns (est. from the skill text)**. Six of those calls only fetch facts in an order the skill fixes. The model already tries to work around this. In the transcripts it chains several commands into one Bash call in 6 of 52 to 21 of 129 cases. It also pipes **35% to 83% of calls** into ad hoc Python to cut the JSON down ([baseline](how-ai-skills-talk-to-gdoc-notes/baseline_today.md)). So "one command, one turn" is not a law, as Codex notes. It is still what usually happens.

Tokens follow turns. Each model call re-read a median of **445k, 317k and 258k tokens** of context in the three sessions with transcripts. A no-op round, where a wait returned, the model looked and then waited again, read **363k to 725k tokens**. gdoc's own bytes are about 1% of a turn. Codex adds a fair caution: most of that context is a cache read, and a cache read costs less and runs faster than fresh input. So token totals do not convert straight into seconds or money ([Anthropic prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)). The direction still holds. Fewer turns save far more than smaller JSON does.

Live mode adds turns that do no work. Of the waits on record, **43 returned on the first poll and 26 ran the full nine minutes**. Each of them ended in a full-context turn. The senior engineer reads the fast returns as gdoc's own replies coming back as news, which would make "a third of wake-ups empty". Codex points out that nobody opened those windows to check their contents. Codex also points out that the counts do not add up: 26 full waits, 94 early returns and 2 interruptions make 122, not the 120 reported. Both points stand until someone looks at the raw wait output ([Codex](how-ai-skills-talk-to-gdoc-notes/codex_second_opinion.md)).

The headline figure, **about 55 s from comment to reply, is an estimate**. It is a 2 to 4 s detection estimate plus the measured 52 s window. It also assumes a session is already waiting. The record has no Claude Desktop runs at all this month, and nobody measured Drive's delay before a new comment shows up. The spec says plainly that with no session open, "a comment written today waits, visible in the document, until a session looks" ([baseline](how-ai-skills-talk-to-gdoc-notes/baseline_today.md)). For a person who writes `ai?` at 10:00 and opens Claude Code at 14:00, the real answer time is four hours, not 55 s. That case is missing from every number above.

## The industry settled on whole jobs, quiet events and thin adapters

Tool makers rarely pick only one route now. Playwright, Chrome DevTools, Stripe, Supabase and Sentry ship a CLI, an MCP server and a skill pack together. Playwright calls its CLI "the best fit" for coding agents and keeps MCP for loops that need "persistent state" ([playwright-cli](https://github.com/microsoft/playwright-cli)). Google's Workspace CLI, the closest peer to gdoc, removed its MCP mode in v0.8.0 and gave no reason ([googleworkspace/cli releases](https://github.com/googleworkspace/cli/releases?q=mcp&expanded=true)). Practitioners report using MCP in Claude Desktop and CLIs in Claude Code ([Checkly](https://www.checklyhq.com/blog/mcp-vs-cli-token-efficiency/)). That is gdoc's split today.

Transport turned out to be a small lever. When the same tool was offered both ways in Claude Code, **MCP was 23% faster and 2.5% cheaper** than the CLI ([Zechner](https://mariozechner.at/posts/2025-08-15-mcp-vs-cli/)). ScaleKit found the CLI 4x to 32x cheaper on GitHub reads. However, all of its MCP failures were network timeouts to a remote server ([ScaleKit](https://scalekit.com/blog/mcp-vs-cli-use)), and that says nothing about a local stdio server like `gdoc mcp`. By mid-2026 the Playwright re-tests found the two routes **within about 1%** of each other on returned output ([DEV Community](https://dev.to/aswani25/playwright-cli-vs-playwright-mcp-which-should-you-use-with-claude-code-1olh)), and sessions ending at 45k to 48k tokens against 48k to 50k ([Checkly](https://www.checklyhq.com/blog/mcp-vs-cli-token-efficiency/)).

What moves the numbers is doing a whole job in fewer turns. Anthropic advises merging multi-step workflows into one tool, such as one `schedule_event` instead of three calls. It also advises concise output by default: 72 tokens against 206 in its Slack example ([Anthropic](https://www.anthropic.com/engineering/writing-tools-for-agents)). In one test, creating a Stripe invoice took **19 steps by CLI, 12 by raw MCP and 4 by code mode** ([Port of Context](https://portofcontext.com/blog/cli-vs-mcp-vs-code-mode)). Vercel cut its agent from about 12 steps to about 7, and from **274.8 s to 77.4 s** ([Vercel](https://vercel.com/blog/we-removed-80-percent-of-our-agents-tools)). Programmatic tool calling saves 37% of tokens on complex tasks. Anthropic's docs say it does not help "strictly sequential workflows where each call depends on Claude reasoning over the previous result" ([Claude docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/programmatic-tool-calling)). A review window is exactly that kind of chain. So for gdoc, fixed job commands beat model-written scripts. Claude Desktop makes the case stronger. One measurement found its MCP calls dispatched **3 to 6 s apart** while the server answered in 50 ms, and the advice was to batch the work into one call ([GitHub issue #76854](https://github.com/anthropics/claude-code/issues/76854)).

State-heavy tools often keep a long-lived process behind a short CLI call. agterm, Obsidian, 1Password and Tailscale all work this way, and so do Playwright's named sessions. None of them publish a latency gain, and each one checks who is calling on the socket. 1Password checks code signatures and expires a session after 10 minutes idle ([1Password](https://www.1password.dev/cli/app-integration-security.md); [tool makers](how-ai-skills-talk-to-gdoc-notes/tool_makers_case_studies.md)). For events, Linear asks an agent to show a sign within **10 seconds** ([Linear](https://linear.app/developers/agents)). `claude-code-action` starts a fresh agent on each `@claude` mention ([claude-code-action](https://github.com/anthropics/claude-code-action)). No vendor publishes how long it takes from an event to the answer.

Claude Code itself offers several ways for an event to wake a session. The Monitor tool is generally available. It feeds each output line back as a notification, and it runs for at most 30 minutes before it must be restarted ([tools reference](https://code.claude.com/docs/en/tools-reference)). An MCP call still running after two minutes moves to the background and reports back when it finishes ([Claude Code MCP](https://code.claude.com/docs/en/mcp)). Channels push events straight into a session, but they are a research preview. They need a development flag or an org allowlist, and a channel that negotiates MCP 2026-07-28 cannot deliver messages ([channels reference](https://code.claude.com/docs/en/channels-reference)). MCP sampling, the protocol's way for a server to borrow the client's model, is deprecated in 2026-07-28 ([MCP changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog)). That rules out letting gdoc ask Claude Desktop's model to judge a comment.

## Twelve options, scored against the stated weights

Every effect figure is an estimate. The rule codes are R1, one JSON object and then exit; R2, the binary prints facts and the skills judge; R3, the binary never prompts; R4, grants die with the process; and R5, no watcher, so the loop starts only when Nail starts it.

The scores apply Codex's corrections, which I checked by hand. **F is 345, not 355. K is 145, not 175. G is 295, not 290.** The other eight scores are right. On the stated weights the order is E, C, F, then A and G tied. The senior engineer's own ranking is different, because it orders by build cost and risk: A, K, H, G, C, F, I, the acknowledgment, E, J, D, B ([senior engineer](how-ai-skills-talk-to-gdoc-notes/senior_engineer_ideas.md)). Both lists need one caution, which Codex raises. These options are parts that stack, not rivals. C's score assumes A is built. F needs A to stay at 3 or 4 turns. B is worth little alone but is a natural home for F. A single league table hides that.

One more correction changes how publish looks. The senior engineer estimates 60 to 75 s from "publish this" to the link on screen. That figure includes a final turn that reports a link which already exists. Your speed measure stops when the result exists. On that measure, today is about 52 to 67 s (est.). Within `publish`, upload to read-back takes 6 to 8 s and read-back to link takes 4 to 6 s ([baseline](how-ai-skills-talk-to-gdoc-notes/baseline_today.md)). So with a folded `publish` and one turn before it, the document would exist after about 15 s and be verified after about 20 s (est.). Measure creation and verification as separate times, as Codex asks.

## Where the senior engineer and Codex disagree, and my call

Both agree on the diagnosis: the model's orchestration costs the most. Both put job-sized commands first and the automatic acknowledgment last. Both say MCP in Claude Code buys consistency and safety, not speed. They differ on five points.

**The resident service.** The senior engineer ranks it last. In that review it only saves TLS setup and repeated reads, about 0.6 to 1.8 s per window (est.), on the quarter of time that is gdoc's. Codex ranks it second and makes it the target: one service per user that watches, keeps cursors, claims work, retries, caches and delivers results, whether or not any conversation is open. Both are right about different things. As a faster transport, the service fixes the wrong cost, and the case studies show no published gain for any daemon. As the owner of watching and state, it is the only place a no-session answer can live. Codex is also right that today's `gdoc mcp` cannot simply grow into it. Each dispatch builds a fresh transport, there is no publish or export, and its one serial worker would make every write wait behind a long watch ([Codex](how-ai-skills-talk-to-gdoc-notes/codex_second_opinion.md)). One fact would settle this: how often a comment arrives while no session is open, and how long it waits. Drive's own timestamps already hold it. For every gdoc reply, subtract the comment's `created` time from the reply's. My call: build the job operations so any host can run them, in a CLI process, in `gdoc mcp` or in a future service. Build the service only when Nail approves unattended answers. Before that decision it holds nothing that a session cannot.

**The independent worker (F).** The senior engineer puts it sixth, behind Nail's decision on R5 and a quality bar. The red-team point behind that is real. The expensive failure in this project was a wrong or unsafe answer, as in the 18 August leak, not a slow one. Codex puts it third and calls it "substantially undervalued", because it takes the large conversation off the critical path. Codex also adds a point the senior engineer missed: a small context does not require a smaller model. That splits the quality risk, which comes from the model and from no human watching, from the token saving, which comes from context size. A replay settles it. Run the same windows through the current session and through an isolated worker on the same model, then rate the answers blind and time both. My call: on your weights, F is the biggest lever on real answer time and on tokens (about 0.6M against 8.6M per live hour, est.). It also carries the largest risk. I would rank it third, after A and the quiet watch. It should start opt-in per document, for `ai?` only, with holds and `ai!` sent to the menu bar app.

**gdoc's own agent (E) against the headless worker (F).** E scores highest of all at 435, and its 15 to 25 s reply is the senior engineer's own estimate, with no vendor figure behind it. Codex wants E benchmarked against F, not parked behind it. I side with the senior engineer on order and with Codex on keeping both open. F reuses Claude Code's tools, skills and billing at build cost M. E is XL and breaks more rules: it adds a credentialed call to a host that is not Google's and a second secret, and it puts the judging inside gdoc. Two measurements decide: `claude -p` start-up time, and the fixed context it loads on Nail's machine. If those dominate F's time or cost, build E.

**Live review in its own session (K).** The senior engineer ranks it second because it costs nothing. Alone it cuts a live hour from 8.6M to about 5.8M tokens (est.), by moving from a mixed session's 445k to 725k context to a dedicated session's 257k to 317k. Codex ranks it ninth and calls it interim. Both are right. K is a habit to adopt this week, not part of the design. Codex's other caution applies too: a smaller context in a dedicated session does not prove that moving the same work saves the same amount. The replay above measures that as well.

**Code execution (D).** The senior engineer ranks it eleventh. Codex ranks it seventh and says no embedded interpreter is needed: the shell already composes calls, and the 35% to 83% piping rate shows the need. I agree with Codex's framing and the senior engineer's order. Give the model batch reads and projections, such as a field mask or a slice around an anchor, so it stops writing parsers. Leave scripting for work across many documents, like "every open `ai?` in every paired document". Anthropic's docs say a sequential chain that reasons at each step gains nothing from code.

Codex also lists gaps that neither ranking covers. They become requirements before any worker runs without a person: one owner per piece of work across all clients, cancellation, rejecting a stale plan, partial completion, and recovery after a crash between a successful write and its receipt. To those it adds coalescing per document, watching suggestions being accepted or rejected, and the laptop going to sleep ([Codex](how-ai-skills-talk-to-gdoc-notes/codex_second_opinion.md)). gdoc already treats the thread as the ledger, where its reply is the receipt. That covers part of crash recovery. It does not cover dedupe while two workers race.

## The recommended route and the first two weeks

The target has four layers, each in one place. **One operation set**: a packet command (`review --work`), a plan command (`respond --from plan.json`) that re-reads each thread as a precondition and runs read-backs in parallel, and a `publish` that folds the build and the marks into itself. **One event source**: a watch that returns only actionable windows and skips gdoc's own echoes. It states that as a fact ("every new item opens with gdoc's mark"), not as a judgement. **Thin adapters**: the CLI in Claude Code and the terminal, `gdoc mcp` in Desktop, and later `gdoc mcp` in Claude Code too, mainly for colleagues who would otherwise get a permission prompt on every Bash call and to give Code the hold rules. The menu bar app keeps reading the presence record. **Pluggable workers**: today the big session; next a fresh context on the same model; then, after Nail's R5 decision, a headless worker per window. That is "one route" in the sense that holds up: one operation table, one rules text and one event record. It is not one transport. Claude Desktop has no push today, and the menu bar app runs no model.

Week one is mostly measurement, as Codex proposes. Record each step of the path: comment created, detected, packet ready, model done, write landed, verified, and reported. Take times from Drive's own timestamps, and include comments that arrived with no session open. In the same week, ship the cheap changes from the senior engineer's first stage. They are a `--follow` watch under the Monitor tool with the echo filter, a `help --brief` of about 200 bytes in place of the 9.6 KB preamble, and live review in its own session. The senior engineer estimates this cuts a live hour to about 4.2M tokens (est.) without changing reply time. Weeks two and three build the packet, the plan command and the parallel read-backs. The aim is at most 2 turns before the last write, a median reply under 35 s from Drive timestamps, `propose` under 4.5 s, and piping below 10% of calls. In parallel, run Codex's replay of identical cases through the session and through an isolated worker. That replay, plus the no-session gap from week one, is what Nail needs to decide on R5. MCP for Claude Code comes after. It must separate the watch from the serial command worker, and it should be A/B tested on one document.

Every idea here keeps R3: the binary still never prompts. A, G and the plan command keep R1 and R4. Only the watch, the service and the workers touch R5. Each break is a `DECISIONS.md` entry, not a refactor.

## Conclusion

The real question is not CLI against MCP. It is where the loop lives. Today the review loop lives in the model's context, so every mechanical step costs a turn that re-reads hundreds of thousands of tokens. Moving the mechanical loop into gdoc, and leaving judgement in one plan the model writes, pays off on every surface at once. It costs no rule beyond a fact-shaped echo filter. Every transport the industry measured lands within a few percent of the others. The turn count is what moves the result.

The decision that would move the speed number most is not technical. It is whether gdoc may answer when nobody is watching. The 55 s figure only describes a session that is already waiting. Nobody has measured the hours a comment waits for a session to open, and Drive's timestamps can measure it this week. If that gap is large, the case for a watcher that outlives a session, and for the service Codex proposes to host it, becomes the main case. If it is small, job-sized commands and a quiet watch are most of the answer.
