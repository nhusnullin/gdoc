What gdoc v2 is

One file you copy onto a machine. No Python, no packages, nothing to install. An agent calls it instead of reading its source and rewriting it to get a job done, which is what happens today.

It publishes documents from your notes, puts other people's documents into the house style without destroying the review already in them, and proposes changes as real suggestions you accept or reject with your own hand. Everything it remembers lives in your own markdown, where you can see it.

How a document lives

Three things working together, and it matters which does what.

The binary deals in facts. What is in the document, what is in your notes, where they differ. It never decides what any of it means. The skill is the judgement: what a comment is asking for, whether two versions have genuinely diverged, what to propose. A comment in the document is simply another door into that same agent, alongside your terminal.

So the same work can be reached two ways, and behaves identically either way.

  1. 1
    You write markdown in the hub
  2. 2
    publish makes a Google Doc It builds a file and uploads it. That route gives the cover, the running head, the logo on page one, a live contents list and page numbers, all at once.
  3. 3
    People read it and comment You mark the ones for the agent with ai:, ai? or ai!.
  4. 4
    A comment is a prompt, and the agent answers it with your hub open Writing ai! in the document does exactly what typing the same instruction to Claude in your terminal does. Same agent, same judgement, and the same context: it reads the markdown the document came from and the folder around it, the notes, the decision log, the raw material. This is the point. A question is answered from what you actually know, not from the words on the page. An instruction is carried out against your material, not against the document in isolation. And if it needs your notes changed, they change in that moment, exactly as they would in a terminal session. Nothing is queued for later.
  5. 5
    gdoc proposes with native suggestions. You decide. Changes arrive as real Google suggestions, with the accept and reject chips your colleagues already know, and a real comment attached to the exact words explaining why. gdoc never accepts and never rejects. That is your hand. Possible because of the Google Developer Preview, granted the same day it was asked for.
  6. 6
    Steps 3 to 5 repeat, for as long as the document is alive Same document, same link, same comment history. Colleagues never get a new URL.
  7. 7
    Alignment is a question you ask, and it runs both ways Has the document drifted from what your notes now say, because somebody edited it in the browser? Or have your notes moved ahead of the document, because a decision landed in that folder and the document has not caught up? Both are drift, and the second is the one that quietly makes a document wrong. It is not a command. The binary can report what each side holds and where they differ. Whether that difference matters is judgement, so it lives in the skill. And it never deletes from your notes: something that exists only there is work not yet published, not drift.
  8. 8
    A PDF is File, Download, PDF In the browser, by you. gdoc has no part in it.

The decisions grouped, not numbered to death

  1. A
    The tool is a binary, and it never prompts Go, one static file, two dependencies. OAuth only, one scope. It emits structured output and exits; Claude does the talking. And it judges whether to ask you. Routine and reversible, it acts. Outward-facing or hard to undo, it stops. A tool that asks permission for everything teaches you to say yes without reading.
  2. B
    Your notes are the source and the memory. Nothing is hidden. No hidden folder. What gdoc knows lives in the front matter of the file it describes. v1 hid its state and it forked: one document had two queues in two folders holding different open items, and a colleague's question sat unanswered in one of them.
  3. C
    gdoc never replaces the body of a document that exists It edits in place, always. Replacing it destroys every comment anchor, including on paragraphs never touched, flattens smart chips so a date chip keeps the words and loses the date, and the API reports all of it as fine. Your colleagues' comments would simply vanish from the screen.
  4. D
    The house style is a text file you can read house.yaml. Colours, fonts, headings, tables, the cover, the logo. A generator builds documents from it. Because you improve the style by asking an agent to look at it and advise you, not by editing Word. So it has to be something an agent can read and something you can review as a diff. v1's template was a Word file, the improvements could not go in it, so they went into code, and the code quietly became the real template.
  5. E
    Restyling has two modes, and the careful one is the default In place keeps every comment, anchor, chip and suggestion, and cannot give the document a first page, a contents list or page numbers. As a new document gives a perfect house style and starts with an empty margin. Copying a document in Drive loses the review no matter how it is done, so any new document begins with nothing. When gdoc sees there is nothing to protect, it says so and offers the better route rather than taking it.
  6. F
    Only a marked comment makes gdoc act A thread stays open once you have used it, so the agent keeps the conversation in mind. But it acts only on a comment carrying an ai marker. Anything else is shown to you and never executed. Nothing is silently ignored, which was v1's failure. And nobody gains the power to drive the agent by replying in a thread you opened.
  7. G
    Everything gdoc writes opens with 🤖 Every comment it leaves starts with the robot. Nothing else, no name, no prefix. Google will not let a tool set an author, so every comment and suggestion gdoc makes is signed with your name and your photo. The marker has one job: to say this was not written by a person. A robot says exactly that, at a glance, in a sidebar with twenty threads in it.
  8. H
    Where it cannot act, it gives you the task A short checklist page in the document, with the exact clicks, listing only what is genuinely missing. You delete it when you are done. A document quietly missing its logo is the tool deciding on your behalf that it did not matter.
  9. I
    Never trust a success When something matters, gdoc checks by a different route that it really happened. In one day, four Google calls returned "OK" while doing something else. One was asked to propose a sentence and rewrote the document instead, silently. Comments reported as healthy had vanished from the screen. Two settings were accepted and never saved.
  10. J
    Copy before you test. Originals are read-only. Your rule, and the same one gdoc follows: it never edits a document it was pointed at, only what it made.

What it cannot do only when restyling in place

Every limitation below applies to one situation only: gdoc styling a document that already exists, which is what happens when a colleague sends you something and you want it in the house style without destroying the review already on it.

A document gdoc creates has none of these problems. Publishing builds a file and uploads it, and that route produces the logo, the contents list, the page numbers, custom style names and everything else, exactly.

So this is the price of not throwing away somebody's comments, and it is paid once, on their document, as a short list of things to click.

  • The logo on page one. Nothing in the API creates a first-page header, and nothing places a floating image.
  • The contents list. No request creates one, in any spelling. You insert it and refresh it.
  • Footer page numbers. Same.
  • Style names of your own. Google's nine can be redefined; a tenth cannot be added.
  • Dot leaders in a contents line, and table styling has to be applied cell by cell, because Google has no idea of a table style.

And one that is not about restyling at all.

Copying a document through the API always loses its comments and suggestions. Drive's own "Make a copy" dialogue has a checkbox for it; the API has no equivalent, and five plausible parameter names were accepted and silently ignored. So any route that produces a new document begins with an empty margin, however it was built.

Twenty live experiments against Google Drive, two adversarial reviews, a Go feasibility study that built every capability rather than surveying it, and a Developer Preview granted the same day it was requested. The full record, with every measurement and every refusal quoted, is in docs/v2/.
